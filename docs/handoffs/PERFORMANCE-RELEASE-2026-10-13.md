# 2026-10-13 Release 原生界面性能补测

## 结论

已自主完成 10k、100k 的三次独立启动/搜索，两个约 60 秒的原生混合列表滚动，以及 100k 下复杂 4K 图片入库、展开、隐藏空闲和反复显示/隐藏。六个场景进程均正常退出，Qt/QML warning 为 0，合成原库未改变。功能断言通过不等于全部性能门禁通过。

**优先改进首屏创建。** 测试宿主首屏可用约 0.91–1.44 秒；Profiler 找到隐藏设置页与未打开对话框的首次创建成本。搜索、滚动代理指标、大图入库和本轮短时资源趋势未发现明显阻断问题。完整发布门禁仍未签核，500k 无结果搜索的历史超线结论保留。

本轮没有修改生产功能或性能策略，只扩展隔离验收工具。主程序 Release 构建成功；QML 常规回归为 16 passed / 0 failed / 2 个未启用的可选场景 skipped。

## 版本、环境与隔离

- 测量时间：2026-10-13 22:28–22:34（Asia/Shanghai）；原始文件使用 UTC。
- Qt 6.11.1 / MinGW GCC 13.1 / Release；实际 QML 和 ThemePalette.js 通过 `qt_add_qml_module` 编译进测试宿主，使用真实 HistoryModel、Queue、Service、Repository、ImageStore。
- Windows 10 22H2，10.0.19045；Ryzen 9 7940HX，32 逻辑处理器；RHI 日志确认选中 NVIDIA RTX 4070 Laptop GPU，D3D11 硬件设备，刷新周期约 6.94 ms（约 144 Hz）。电源方案观察为“平衡”。GPU 驱动、供电状态和磁盘介质未获取，正式 Ref-01 未冻结。
- Qt 管线磁盘缓存在测试宿主中关闭；不清空 OS 文件缓存，不把三次独立进程称为三个 OS 冷启动。
- 剪贴板、系统托盘和热键边界使用替身。每次运行将已有合成库复制到 QTemporaryDir 后使用，拒绝存在 WAL 的源库。记录和图片只写测试副本；没有读写用户历史或系统剪贴板。
- [环境记录](../acceptance/2026-10-13-performance/environment.json)、[源码/二进制/源库哈希和退出码](../acceptance/2026-10-13-performance/manifest.json)；六轮结束时 `HashesUnchanged=true`。

## 启动和搜索

启动计时从测试副本准备完成后的 Queue 创建开始，含等待数据服务初始化、编译 QML 的实例化、第一批记录以及可见窗口首帧。**不含进程创建、QGuiApplication 初始化、生产 bootstrap/托盘/采集器，也不是正式主程序启动耗时。** QtTest 的多次等待各有约 50 ms 轮询粒度，“首屏可用”是保守的观测上界；服务初始化的串行等待也区别于生产启动。

搜索计时从 `HistoryModel::setFilter` 到 `loadingChanged(false)`，每进程分别 30 个命中和 30 个无命中样本；校验命中行非空、无命中行为空，全库总数一直保持 10k/100k。应用的 250 ms 输入防抖未计入；未将模型完成当作结果已显示到屏幕的精确时刻。

## 原生列表滚动

每种规模一轮约 60 秒；每 16 ms 修改原生 ListView.contentY，并在已加载区域往返。真实 delegate、模型分页与图片加载参与，但未注入鼠标滚轮，也不包含 Windows 输入链路和 WheelHandler 的精确惯性行为。两轮各 59 个资源采样均记录窗口 exposed=true。

混合夹具为 70% 文本、20% 图片引用、10% 合成本地文件路径。图片引用复用两张简单色块图，属于缓存友好的浏览场景；复杂图另行入库和展开，不称为复杂照片混合列表全覆盖。

帧记录来自 render-thread `QQuickWindow::frameSwapped`。统计首尾各排除 2 秒，留下约 56 秒。**这是帧交换完成间隔代理，不是 GPU 执行耗时，也不是显示器实际 Present 时间。**

| 数据量 | 交换间隔数 | P95（ms） | 最大（ms） | >33.3 ms | >100 ms | GUI 16 ms 心跳最大（ms） |
|---|---:|---:|---:|---:|---:|---:|
| 10k | 7917 | 7.74 | 40.20 | 1（0.013%） | 0 | 50.40 |
| 100k | 7917 | 8.26 | 45.89 | 2（0.025%） | 0 | 49.51 |

本场景未观察到 >100 ms 的代理间隔或 GUI 心跳延迟。持续滚动时 CPU 约 35.47% / 33.83%，分母为一个逻辑核心；不能直接当成任务管理器按 32 逻辑处理器归一化的百分比。采样 RSS 峰值约 191.48 / 185.66 MiB，离散采样可能漏掉短峰。

## 复杂 4K 图片与展开

100k 进程中预先构造固定 seed 的高熵 3840×2160 图；十次只改变独立像素以保证唯一记录，逐张提交到真实后台队列，保存期间列表继续滚动。不是实际照片/截图，也不经过 Windows QClipboard/MIME 快照。生成夹具不在提交至提交完成的计时内。

- 10/10 接受并成功提交，最终全库总数 100010；最后一张通过服务读取并逐像素比较一致。
- 提交到观测到提交完成：P50 **913.34 ms**，P95/最大 **1007.35 ms**。QtTest 轮询使其为观测上界；十个样本仅作补测基线，少于正式要求的至少 30 样本/三进程。
- 保存期间 GUI 心跳 P95 **31.62 ms**，最大 **36.73 ms**，没有 >100 ms 延迟。
- 顶部复杂图片五次展开/收起：展开检查 P50 **223.83 ms**，P95/最大 **250.90 ms**；包含主动等待 50 ms 及 Image.Ready 的轮询，只是响应上界，不是精准的显示完成时间。
- 未采集大图阶段的连续 RSS/OS 高水位，因此不签大图峰值内存门槛。未覆盖突发多张并行采集或 Windows 真实剪贴板通知的性能。

## 隐藏窗口与反复呼出

是真实 QQuickWindow.hide/show；测试托盘替身不创建 Shell 图标，也没有生产采集器。隐藏 120 秒；之后每 500 ms 切换显示状态，持续 60 秒（约 60 个显示/隐藏周期）。

| 场景 | 单核心 CPU 平均 | RSS 首/末（MiB） | 采样峰值（MiB） | RSS 前/后 1/3 中位（MiB） |
|---|---:|---:|---:|---:|
| 隐藏空闲 | 0.234% | 142.42 / 114.43 | 142.42 | 137.32 / 114.43 |
| 反复显示/隐藏 | 0.078% | 117.66 / 113.59 | 117.80 | 117.68 / 113.48 |

此短场景没有持续 RSS 增长证据；不宣称无限期无泄漏。反复呼出时帧交换约每秒一次是显示/隐藏驱动造成的预期静止间隔，不能误判为一秒卡顿。

## 首屏热点定位

另外在既有 `build/Perf-QmlProfiler` 用 Release + `-DQT_QML_DEBUG` 构建隔离宿主，采集逻辑类事件；绝对耗时不混入以上无 Profiler 的基线。

[独立热点报告](../../profiler/reports/profile-report-acceptance-startup-2026-10-13-224026.md)、[原始 trace](../../profiler/traces/qmlprofiler-trace-acceptance-startup-2026-10-13-224026.qtd)、[解析 JSON](../acceptance/2026-10-13-performance/startup-profiler-parsed.json)。Profiler 与被测进程正常退出，trace 约 6.69 MB，无 Qt/QML warning。

隐藏设置页仍立即创建。设置分区图标容器的一次首次创建区间 **382.57 ms**；同位置其余九次合计很小，不是每个分区都要 38 ms。导入对话框 standardButtons 的一次区间 **87.98 ms**，对应 JS 本身约 0.093 ms，不能指责常量表达式运算缓慢。建议下一步用按需 Loader 创建设置页和少用对话框，保留配置初始化/平台注册生命周期；改后重测首屏和首次打开设置的体验。

另有无源码位置的 Creating 区间，不能自行归因到项目函数；需要更细的 CPU 栈采样时再定位。

## 测试工具问题与证据保留

预检失败不计入软件性能失败：旧合成临时目录仅允许沙箱账号读，复制到正常继承权限的项目夹具目录后解决；新增测试 QML 模块首次遗漏 ThemePalette.js，随后补齐；搜索断言最初把全库 totalCount 当成过滤结果数，已改为校验 rowCount 且确保 totalCount 不变。三份 pilot 日志保留。

第一次 Profiler 启动没有 trace，原因是旧 `build/Perf-QmlProfiler` 中残留 Qt 6.2.2 的本地 DLL。将新宿主部署到独立目录并用 Qt 6.11.1 windeployqt 部署后成功。不删除旧运行库，不将 loader 失败作为当前应用崩溃。

六轮结束后补强测试驱动的退出顺序：销毁窗口/渲染线程后才让直接帧回调的局部样本离开作用域。一次新的原生 quick 回归通过，生产 EXE 哈希未变；不把这次 quick 计为第四轮完整基线。测量时的 [测试源码快照](../acceptance/2026-10-13-performance/tst_qml_acceptance-measured.cpp) 和 [CMake 快照](../acceptance/2026-10-13-performance/CMakeLists-measured.txt) 匹配原 manifest；[退出回归清单](../acceptance/2026-10-13-performance/cleanup-regression-manifest.json) 记录后续测试工具版本。

原生预检中还观察到 Qt 默认管线缓存写入系统用户的 LocalAppData 测试命名空间。主程序源码未指定管线缓存目录，推断正式运行也可能产生该缓存，仍需修正到数据目录或明确禁用才能满足“全部信息在程序目录”的要求。本轮测试宿主已禁用自动管线磁盘缓存。

## 复现与剩余项

1. 在 Qt Creator 的同一 Release 构建中构建 ClipboardHistory 和 tst_qml_acceptance。
2. 准备固定 seed 生成器的 10000/100000 合成库到 `build/performance-fixtures-20261013/<rows>/history.sqlite3` 和同级 images；不要指定实际用户库。本轮来源为既有 `build/Perf-Baseline/perf-data-CoMotI`，源文件哈希在 manifest 中。
3. 从项目根执行 `tests/acceptance/run_release_performance.ps1 -RunName 2026-10-13-performance-repeat1`，证据写入 `docs/acceptance/<RunName>`。脚本拒绝覆盖既有 run JSON/TXT；原执行脚本也有[快照](../acceptance/2026-10-13-performance/run_release_performance-measured.ps1)。首轮各跑长场景，另两轮只测独立启动和搜索。
4. [汇总 JSON](../acceptance/2026-10-13-performance/summary.json) 和六份原始 run JSON/TXT 均保留；每个全程输出退出码，不靠肉眼宣称成功。
